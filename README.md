# Визуализатор графа зависимостей пакетов

Дисциплина «Конфигурационное управление», практическая работа №2,
вариант 23. Группа ИКБО-66-25.

## 1. Общее описание

Инструмент визуализации графа зависимостей для менеджера пакетов
Rust (Cargo). Готовые менеджеры пакетов и библиотеки для получения
зависимостей не используются. Нужен только Python 3, сторонние пакеты
не требуются.

Реализованы этапы:

1. Конфигурация: параметры читаются из файла YAML и проверяются.
2. Сбор данных: прямые зависимости пакета Rust (Cargo) берутся
   из репозитория crates.io по URL-адресу.
3. Основные операции: граф всех (в том числе транзитивных) зависимостей
   строится обходом BFS с рекурсией, циклы обрабатываются, есть режим
   тестового репозитория.
4. Дополнительные операции: режим вывода обратных зависимостей (какие
   пакеты зависят от заданного) тем же обходом BFS.
5. Визуализация: граф выводится на экран на языке диаграмм Graphviz
   (DOT), результаты сравнены с штатным инструментом `cargo tree`.

## 2. Функции и настройки

### Конфигурационный файл

Параметры задаются в файле формата YAML. По умолчанию читается
`config.yaml` из текущей папки, другой файл можно передать аргументом.

    package: serde
    repository: https://crates.io
    test_mode: false

- **`package`**: имя анализируемого пакета. Латинские буквы, цифры,
  `_` и `-`, начинается с буквы, не длиннее 64 символов.
- **`repository`**: URL-адрес репозитория или путь к файлу тестового
  репозитория. При `test_mode: false` это URL `http://` или `https://`,
  при `test_mode: true` путь к существующему файлу.
- **`test_mode`**: режим работы с тестовым репозиторием, `true`
  или `false`.
- **`reverse`** (необязательный, по умолчанию `false`): режим вывода
  обратных зависимостей, `true` или `false`. Работает только
  при `test_mode: true`.

Поддерживается подмножество YAML: пары «ключ: значение»,
комментарии после `#`, строки в кавычках, значения `true` и `false`.

### Прямые зависимости из crates.io (этап 2)

Для пакета берётся его последняя стабильная версия, затем список её
зависимостей. Используется открытый API репозитория и только модули
`urllib` и `json` стандартной библиотеки, cargo не вызывается:

    {repository}/api/v1/crates/{package}                       версия пакета
    {repository}/api/v1/crates/{package}/{version}/dependencies   зависимости

Правила отбора:

- зависимости для разработки (`dev`, нужны только для тестов самого
  пакета) пропускаются;
- обычные зависимости и зависимости сборки (`build`) учитываются;
- если имя встречается несколько раз (для разных платформ), оно
  берётся один раз;
- необязательные зависимости (`optional`, подключаются через features)
  в граф не входят.

### Граф зависимостей (этап 3)

Граф строится обходом в ширину (BFS) с рекурсией (`src/graph.py`):
функция обрабатывает один уровень графа (сначала сам пакет, затем
его прямые зависимости, затем их зависимости) и рекурсивно вызывает
себя для следующего уровня, пока он не пуст.

Циклические зависимости обрабатываются: пакет, который уже есть в графе
или уже стоит в очереди, второй раз не обходится. Поэтому цикл
`A -> B -> C -> A` и пакет, зависящий от самого себя, не приводят
к бесконечной работе, а каждое ребро выводится один раз.

На этапах 3 и 4 граф выводился текстом («A -> B, C»), с этапа 5 он
выводится на языке Graphviz. Вывод прямых зависимостей был нужен
только на этапе 2, а вывод параметров «ключ = значение» на этапе 1.

### Обратные зависимости (этап 4)

При `reverse: true` выводятся пакеты, которые зависят от заданного,
напрямую или через другие пакеты. Используется тот же обход BFS
с рекурсией, что и на этапе 3 (`build_graph`), только по перевёрнутым
рёбрам: функция `reverse_edges` из описания «A зависит от B и C»
делает «от B зависит A, от C зависит A». Циклы обрабатываются так же.

Для пакета D из ромба (A -> B, C -> D) получаются B, C и через них A.
На языке Graphviz стрелки по-прежнему означают «зависит от»:

    digraph dependencies {
        node [shape=box];
        "D" [style=filled, fillcolor=lightblue];
        "B" -> "D";
        "C" -> "D";
        "A" -> "B";
        "A" -> "C";
    }

Режим работает с тестовым репозиторием: чтобы найти все пакеты, которые
зависят от заданного, нужно знать весь репозиторий. В crates.io
от популярных пакетов зависят десятки тысяч других, поэтому при
`test_mode: false` параметр `reverse: true` считается ошибкой.

### Визуализация на языке Graphviz (этап 5)

Граф, построенный обходом BFS, переводится в текст на языке диаграмм
Graphviz (`src/dot.py`) и выводится на экран. Каждое ребро `"A" -> "B"`
означает «A зависит от B», анализируемый пакет выделен цветом, каждый
пакет и каждое ребро встречаются один раз.

Нарисовать картинку можно программой Graphviz или в браузере
(например, https://dreampuf.github.io/GraphvizOnline, вставить вывод):

### Сравнение с cargo tree

Штатный инструмент Cargo для просмотра зависимостей: `cargo tree`.
Для сравнения создан пустой проект с зависимостями `serde = "1"`,
`rand = "0.10"`, `clap = "4"` и выполнено `cargo tree -p ИМЯ`
(cargo 1.97.0, версии пакетов на 30.10.2026).

**serde**

    $ cargo tree -p serde
    serde v1.0.229
    └── serde_core v1.0.229

    $ cargo tree -p serde --target all
    serde v1.0.229
    └── serde_core v1.0.229
        └── serde_derive v1.0.229 (proc-macro)
            ├── proc-macro2 v1.0.107
            │   └── unicode-ident v1.0.27
            ├── quote v1.0.47
            │   └── proc-macro2 v1.0.107 (*)
            └── syn v3.0.9
                ├── proc-macro2 v1.0.107 (*)
                ├── quote v1.0.47 (*)
                └── unicode-ident v1.0.27

Расхождение 1, платформы. Зависимость serde_core -> serde_derive
записана с условием `target = cfg(any())`, которое не выполняется ни
на одной платформе (так авторы serde связывают версии двух пакетов).
`cargo tree` проверяет такие условия и по умолчанию показывает только
зависимости для текущей платформы. Наш инструмент условия `target`
не проверяет и берёт зависимости для всех платформ. С флагом
`--target all` cargo показывает те же 7 пакетов.

Расхождение 2, features. Ребра syn -> quote у нас нет: эта
зависимость необязательная (`optional`) и подключается возможностью
`printing`, которую включает serde_derive. Наш инструмент
необязательные зависимости не берёт.

**rand**

    $ cargo tree -p rand
    rand v0.10.3
    ├── chacha20 v0.10.2
    │   ├── cfg-if v1.0.5
    │   ├── cpufeatures v0.3.1
    │   └── rand_core v0.10.1
    ├── getrandom v0.4.3
    │   ├── cfg-if v1.0.5
    │   ├── libc v0.2.191
    │   └── rand_core v0.10.1
    └── rand_core v0.10.1

Расхождение, features. chacha20 и getrandom у rand необязательные,
их подключают возможности по умолчанию (`default = ["std", "std_rng",
"sys_rng", "thread_rng"]`). Cargo включает возможности по умолчанию,
наш инструмент их не учитывает. Если отключить их
(`rand = { version = "0.10", default-features = false }`), вывод
совпадает с нашим:

    $ cargo tree -p rand
    rand v0.10.3
    └── rand_core v0.10.1

**clap**

    $ cargo tree -p clap
    clap v4.6.7
    └── clap_builder v4.6.7
        ├── anstream v1.0.0
        │   ├── anstyle v1.0.14
        │   ├── anstyle-parse v1.0.0
        │   │   └── utf8parse v0.2.2

Расхождение, features. anstream и strsim у clap_builder необязательные,

С `clap = { version = "4", default-features = false, features = ["std"] }`
вывод совпадает с нашим:

    $ cargo tree -p clap
    clap v4.6.7
    └── clap_builder v4.6.7
        ├── anstyle v1.0.14
        └── clap_lex v1.1.1

**Общие отличия**

- `cargo tree` рисует дерево: общая зависимость повторяется под каждым
  пакетом, а повторы помечаются `(*)`. У нас граф: каждый пакет и
  каждое ребро выводятся один раз, у общей зависимости несколько
  входящих стрелок.
- `cargo tree` показывает версии. Мы берём последнюю стабильную версию
  каждого пакета, а cargo выбирает последнюю версию, подходящую под
  требование (например, `syn ^3`) и под версию Rust. Для этих примеров
  версии совпали, для старых пакетов они могут отличаться.
- Необязательные зависимости (features) и условия платформ (`target`)
  наш инструмент не вычисляет: это работа настоящего менеджера пакетов,
  а готовые менеджеры пакетов по условию задания использовать нельзя.

### Тестовый репозиторий

При `test_mode: true` параметр `repository` указывает на текстовый файл
с описанием графа. Пакеты называются большими латинскими буквами,
каждая строка описывает пакет и его прямые зависимости через пробел:

    # комментарий
    A: B C
    B: D
    C: D
    D:

Каждый пакет, на который есть ссылка, тоже должен быть описан
(пакет без зависимостей записывается как `D:`). Это проверяется
сразу при чтении файла.

### Ошибки

Проверяются все параметры конфигурации, и все найденные ошибки
выводятся сразу. При любой ошибке программа завершается с кодом 1.

| Ситуация | Сообщение |
|----------|-----------|
| нет конфигурационного файла | `конфигурационный файл не найден: ...` |
| строка без двоеточия | `строка 2: ожидается запись вида «ключ: значение»` |
| ключ повторяется | `строка 3: ключ «package» повторяется` |
| незакрытая кавычка | `строка 2: незакрытая кавычка` |
| параметр не задан | `repository: параметр не задан` |
| лишний параметр | `depth: неизвестный параметр` |
| пустое имя пакета | `package: не задано имя анализируемого пакета` |
| некорректное имя пакета | `package: некорректное имя пакета «1 bad name!» ...` |
| некорректный URL | `repository: некорректный URL-адрес «crates.io» ...` |
| нет файла тестового репозитория | `repository: файл тестового репозитория не найден: ...` |
| неверный режим | `test_mode: ожидается true или false, получено «maybe»` |
| неверный режим обратных зависимостей | `reverse: ожидается true или false, получено «maybe»` |
| reverse без тестового репозитория | `reverse: обратные зависимости поддерживаются только при test_mode: true` |

Ошибки репозитория:

| Ситуация | Сообщение |
|----------|-----------|
| пакета нет в crates.io | `пакет не найден в репозитории: ...` |
| сервер недоступен или нет сети | `не удалось подключиться к репозиторию: ...` |
| сервер ответил не JSON | `репозиторий вернул не JSON: ...` |
| другая ошибка HTTP | `репозиторий вернул ошибку 500: ...` |
| пакет не описан в тестовом репозитории | `пакет D не описан в тестовом репозитории (на него ссылается B)` |
| анализируемого пакета нет в тестовом репозитории | `пакет Z не описан в тестовом репозитории` |
| имя не из больших латинских букв | `строка 2: некорректное имя пакета «c» ...` |
| строка тестового репозитория без двоеточия | `строка 2: ожидается запись вида «A: B C»` |
| пакет описан дважды | `строка 3: пакет A описан повторно` |

## 3. Сборка и тесты

Сборка не нужна, достаточно Python 3.8 или новее.

    sh run.sh                          запуск с config.yaml
    sh run.sh examples/stage3/test_cycle.yaml   запуск с другим файлом
    sh scripts/run_tests.sh            автотесты
    sh scripts/stage1_demo.sh          демонстрация ошибок конфигурации
    sh scripts/stage2_demo.sh          пакеты crates.io и ошибки репозитория
    sh scripts/stage3_demo.sh          граф на разных тестовых репозиториях
    sh scripts/stage4_demo.sh          обратные зависимости
    sh scripts/stage5_demo.sh          граф на языке Graphviz для serde, rand, clap

Скрипт `stage3_demo.sh` запускает приложение со всеми файлами из
`examples/stage3`:

- `test_single`: пакет без зависимостей;
- `test_diamond`: ромб, общая зависимость D входит в граф один раз;
- `test_cycle`: цикл A -> B -> C -> A;
- `test_self_loop`: пакет зависит сам от себя;
- `test_big`: 8 пакетов, несколько уровней и два цикла;
- `test_big_from_C`: тот же репозиторий, анализ начинается с пакета C;
- `test_err_*`: ошибки тестового репозитория;
- `real_serde`, `real_clap`: настоящие пакеты из crates.io.

Скрипт `stage4_demo.sh` запускает приложение со всеми файлами из
`examples/stage4` (репозитории те же, что на этапе 3):

- `diamond_D`: от D зависят B, C и через них A;
- `diamond_B`: от B зависит только A;
- `diamond_A`: от A никто не зависит;
- `cycle_A`: обратные зависимости в цикле A -> B -> C -> A;
- `self_loop_B`: пакет A зависит сам от себя и от B;
- `big_H`: от H зависят все 7 остальных пакетов большого графа;
- `big_G`: от G зависят C, A, D (два цикла);
- `big_A_forward`: тот же репозиторий с `reverse: false` для сравнения;
- `err_*`: неизвестный пакет, неописанный пакет, неверное значение
  `reverse`, `reverse: true` для crates.io.

Скрипт `stage5_demo.sh` выводит граф на языке Graphviz для трёх пакетов
crates.io (serde, rand, clap) и для большого тестового репозитория
в прямом и обратном режимах.

Начиная с этапа 5 все примеры выводят граф на языке Graphviz.

Для `stage2_demo.sh`, `stage5_demo.sh` и примеров `real_*` нужен доступ
в интернет.
Автотесты сеть не используют: ответы сервера в них подменяются.
